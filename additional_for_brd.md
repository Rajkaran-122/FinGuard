### ADD AS NEW SECTION 6.2 — RBAC Implementation Detail

**Insert after section 6.1:**

**6.2 FastAPI Dependency Injection Pattern for RBAC**

Access control in this system is implemented using FastAPI's native Depends() system. Every protected route declares its permission requirement as a dependency in the function signature — not inside the handler body. This means:

- Security requirements are visible at a glance when reading any route file
- RBAC logic lives in one place (core/dependencies.py) and is reused across all routers
- Unit testing RBAC requires only injecting a mock user object — no HTTP layer needed
- The Swagger UI at /docs automatically shows the lock icon and OAuth2 flow for every protected endpoint

The dependency chain for every protected request is:

```
oauth2_scheme (extract Bearer token)
    → get_current_user (decode JWT → re-fetch user from DB → check status)
        → require_role("admin") (check role → raise 403 or pass through)
            → route handler (receives current_user as a verified, typed object)
```

Re-fetching the user from the database on every request (rather than trusting the JWT payload alone) ensures that deactivated users are blocked immediately — even if their token has not yet expired.

### ADD TO SECTION 7 — Data Model Requirements

**Add as section 7.3:**

**7.3 SQLAlchemy Implementation Notes**

- UUIDs are generated at the application layer using Python's uuid.uuid4() — this avoids database-specific UUID generation syntax and keeps the model portable across SQLite and PostgreSQL
- All Enum fields (role, type) are implemented as Python Enum classes and mapped to SQLAlchemy Enum columns — this enforces valid values at both the application and database layers
- Soft delete is implemented via a deleted_at TIMESTAMPTZ column (NULL = active) rather than an is_deleted boolean — this preserves the deletion timestamp for audit purposes and allows future queries like "records deleted in the last 30 days"
- All queries against financial_records include .filter(FinancialRecord.deleted_at.is_(None)) — deleted records are invisible to all API consumers
- SQLite WAL (Write-Ahead Logging) mode is enabled via PRAGMA journal_mode=WAL on every connection — this allows concurrent readers while a write is in progress
- Foreign key enforcement is enabled via PRAGMA foreign_keys=ON — SQLite disables this by default

**FastAPI vs Flask vs Django REST Framework — Decision Rationale:**

Flask requires manual setup for validation, documentation, and dependency injection — three things that are critical for this system and come free with FastAPI. Django REST Framework is a mature choice but carries significant overhead and convention for what is a focused API system. FastAPI is purpose-built for API development, outperforms both in benchmarks, and its Pydantic integration means the validation layer and the documentation layer are generated from the same schema definitions — eliminating an entire class of documentation drift bugs.

**Add as section 9.6 — Database Strategy:**

**9.6 Data Persistence Strategy**

SQLite is used as the persistence layer. This is not a compromise — it is the correct tool for this scope. The specific justification is:

- SQLite is fully ACID-compliant with WAL mode enabled — data integrity is guaranteed
- All SQL aggregation functions used in dashboard APIs (SUM, COUNT, GROUP BY, strftime for date truncation) are natively supported
- A single file database means any evaluator can clone the repository and have a running system in under two minutes with zero infrastructure
- SQLAlchemy ORM means no code changes are required to move to PostgreSQL — only the DATABASE_URL environment variable changes
- For write-concurrent production use, the migration path is: change DATABASE_URL to a PostgreSQL connection string, run alembic upgrade head — done

The SQLite file is located at finance.db in the project root for local development and at /data/finance.db on Render.com's persistent disk for deployment.

### ADD TO SECTION 11 — Assumptions & Constraints

**Add to section 11.1 — Assumptions:**

- FastAPI's automatic Swagger UI at /docs serves as the primary API documentation — a separate Postman collection is provided as supplementary material but /docs is the source of truth
- All Enum values (role, record type, category) are validated at the Pydantic schema layer — unknown values are rejected with 422 before reaching the service layer
- The deleted_at column approach is used for soft delete rather than is_deleted boolean — this preserves deletion timestamps and is more information-rich for future audit queries
- Token re-validation against the database on every request is intentional — this ensures deactivated users are blocked immediately even within a valid token's 24-hour window
- WAL mode and foreign key enforcement are set via SQLite PRAGMA on every connection — these are not persistent SQLite settings and must be applied at connection time

**Add to section 11.2 — Constraints:**

- SQLite does not support true concurrent writes from multiple processes — for multi-instance deployment, DATABASE_URL should be changed to PostgreSQL with zero code changes required
- JWT tokens cannot be server-side invalidated before expiry in v1 — deactivation is enforced by re-fetching user status from DB on each request, which achieves the same practical effect
- SQLite's strftime function is used for monthly trend grouping — this is SQLite-specific syntax; the equivalent in PostgreSQL is DATE_TRUNC, which would require a one-line query change
